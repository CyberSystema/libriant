# A5-secrets-config

Reviewed apps/api/src/config/env.ts (env schema/validation), scripts/secrets.ts (interactive secrets manager), scripts/ensure-env.sh (deploy-time generator), the .env.example / .env.prod.example templates, and infra/compose/docker-compose.prod.yml. Secret enforcement is genuinely solid: SESSION_SECRET / ADMIN_SESSION_SECRET / IMPERSONATION_SECRET / STORAGE_SIGNING_SECRET / MFA_MASTER_KEY are all REQUIRED in non-dev with a 24-char minimum (64-hex for MFA, validated at MfaService boot), dev-only static fallbacks never apply outside development, Stripe API key + webhook secret both throw at boot when STRIPE_DRIVER=real, numeric coercion fails loudly on bad input, no hardcoded secrets exist in source, and .env.local/.env.prod are gitignored (only the example templates are tracked). The real gaps are two config-drift / fail-open-precondition issues, not weak secrets: (1) RESEND_API_KEY is read by env.ts and the email worker but is injected by NEITHER the api nor worker in the prod compose, so the documented EMAIL_DRIVER=resend path crash-loops at boot; (2) the SESSION_COOKIE_SECURE='auto' default only forces Secure when NODE_ENV==='production' exactly, so a non-production/non-development deploy (e.g. staging) on the http PUBLIC_APP_URL default silently ships non-Secure, non-__Host- session/admin/impersonation cookies.

## [HIGH] RESEND_API_KEY never reaches the containers — documented EMAIL_DRIVER=resend path crash-loops the api + worker at boot  _[skeptic: confirmed high]_
- **file**: `infra/compose/docker-compose.prod.yml:74 (x-app-env) and apps/api/src/config/env.ts:360`
- **verified**: static | **confidence**: high
- **evidence**: env.ts reads it: `resendApiKey: process.env.RESEND_API_KEY?.length ? process.env.RESEND_API_KEY : null` (env.ts:360), and the Resend driver hard-fails without it: `if (!env.resendApiKey) { throw new Error('EMAIL_DRIVER=resend requires RESEND_API_KEY (re_...).'); }` (apps/api/src/email/drivers/resend-driver.ts:31-33). The prod compose x-app-env block injects SMTP_URL/EMAIL_FROM/EMAIL_DRIVER but NOT RESEND_API_KEY — `grep -rn RESEND infra/` returns nothing. The block's own comment warns this is load-bearing: 'every driver var the app reads MUST be listed here — Compose only injects variables referenced in this block, not everything in .env.prod' (compose lines 56-57). Deploy sources the file (`set -a; . /srv/libriant/.env.prod; set +a`, deploy.yml) so RESEND_API_KEY is in the host shell, but Compose drops any var it doesn't reference. The worker builds the same driver: `const driver = createEmailDriver()` (apps/api/src/email/email-worker.ts:64) and inherits `<<: *app-env` (compose:239).
- **impact**: An operator who follows .env.prod.example (lines 77-78 document RESEND_API_KEY for EMAIL_DRIVER=resend) and sets EMAIL_DRIVER=resend + RESEND_API_KEY in /srv/libriant/.env.prod gets resendApiKey=null inside the container; both the api and the email worker throw at construction and crash-loop. Fail-closed (no silent insecure send), but it breaks a first-class, documented production email backend and would manifest as a failed deploy with a misleading 'requires RESEND_API_KEY' error even though the operator DID set it.
- **fix**: Add `RESEND_API_KEY: ${RESEND_API_KEY:-}` to the x-app-env block in infra/compose/docker-compose.prod.yml (next to SMTP_URL) so it propagates to both api and worker; mirror it in .env.prod.example management if needed.
- **skeptic verdict**: real=True sev=high — Independently confirmed across the full chain. (1) RESEND_API_KEY is documented in .env.prod.example as the var to set for EMAIL_DRIVER=resend (lines 72 "EMAIL_DRIVER=resend + RESEND_API_KEY=re_..." and 78 "RESEND_API_KEY="). (2) env.ts reads it ONLY from process.env: `resendApiKey: process.env.RESEND_API_KEY?.length ? process.env.RESEND_API_KEY : null` (apps/api/src/config/env.ts:360). (3) The factory eagerly constructs the driver when EMAIL_DRIVER=resend: `case 'resend': return new ResendEmailDriver();` (apps/api/src/email/drivers/create-email-driver.ts:18-19), and that constructor throws if the key is absent: `if (!env.resendApiKey) { throw new Error('EMAIL_DRIVER=resend requires RESEND_API_KEY (re_...).'); }` (resend-driver.ts:30-33). (4) The compose x-app-env block (docker-compose.prod.yml:34-86) passes SMTP_URL/EMAIL_FROM/EMAIL_REPLY_TO through with ${VAR:-} but never lists RESEND_API_KEY; `grep -rn RESEND infra/` returns nothing. There is NO env_file: directive anywhere in the compose file, so Compose only injects variables it explicitly references in the environment block — a host-shell var not named there does NOT reach the container. (5) Deploy sources .env.prod into the host shell (`set -a; . /srv/libriant/.env.prod; set +a`, deploy.yml:260,352), so the operator's RESEND_API_KEY lives in the shell but is dropped by Compose. (6) The worker inherits the same block (`<<: *app-env`, compose:239) and builds the same driver. Net effect: an operator who follows the documented resend path and sets EMAIL_DRIVER=resend + RESEND_API_KEY in .env.prod gets resendApiKey=null inside the container, and both the api and worker throw at construction and crash-loop with a misleading 'requires RESEND_API_KEY' error even though they set it. I could not refute it: there is no env_file fallback, no alternate pass-through, and the resend arm is reachable. Severity: high rather than critical — it is fail-closed (no silent insecure send; no data exposure), needs the precondition of choosing the resend backend, and a working SMTP alternative is wired through. But it silently breaks a first-class documented production email backend and produces a deceptive error, which is a real deploy-blocking ops defect. The proposed fix (add `RESEND_API_KEY: ${RESEND_API_KEY:-}` to x-app-env) is correct and mirrors the existing SMTP_URL treatment.

## [MEDIUM] Cookie Secure / __Host- prefix fails open on any NODE_ENV that is not exactly 'production' (e.g. staging)
- **file**: `apps/api/src/config/env.ts:224-235`
- **verified**: static | **confidence**: medium
- **evidence**: `const cookieSecure = optional('SESSION_COOKIE_SECURE', 'auto'); const isSecure = cookieSecure === 'auto' ? (nodeEnv === 'production' || optional('PUBLIC_APP_URL','http://localhost:3000').startsWith('https://')) : cookieSecure === 'true';`. The forced-Secure leg checks `nodeEnv === 'production'` EXACTLY. Secret-requirement logic elsewhere uses the safer `isDev = nodeEnv === 'development'` (anything non-dev is treated as prod), but the cookie leg does not. isSecure flows into Secure flag AND the __Host- prefix for all three cookies: cookie.service.ts:18/31, admin-cookie.service.ts:19/25, impersonation-cookie.service.ts:13/19, and the cookie-name defaults at env.ts:272-301 (`isSecure ? '__Host-libriant_session' : 'libriant_session'`).
- **impact**: A deploy with NODE_ENV=staging (a common value) that leaves SESSION_COOKIE_SECURE unset/'auto' and PUBLIC_APP_URL on the http default resolves isSecure=false, sending session/admin/impersonation bearer cookies WITHOUT Secure and without the __Host- prefix — they can leak over a plaintext/mixed request. The shipped prod compose hardcodes NODE_ENV=production AND SESSION_COOKIE_SECURE='true', so the official deploy path is safe; the exposure is for any non-compose / staging deploy that relies on the 'auto' default.
- **fix**: Treat all non-development environments as Secure-by-default: change the auto leg to `nodeEnv !== 'development' || PUBLIC_APP_URL.startsWith('https://')`, matching the isDev convention already used for secret enforcement.

## [LOW] Admin can enable plan/quota billing at runtime while STRIPE_DRIVER=fake — checkout/portal silently run the in-memory stand-in in production
- **file**: `apps/api/src/platform-settings/platform-settings.service.ts:32-42 and infra/compose/docker-compose.prod.yml:61-62`
- **verified**: static | **confidence**: medium
- **evidence**: billingEnabled() returns the platform_settings DB row when present, else the env default (platform-settings.service.ts:39). The admin 'Subscriptions' toggle writes that row (setBillingEnabled, lines 45-55) with no check on the resolved Stripe driver. Prod compose defaults are independent: `BILLING_ENABLED: ${BILLING_ENABLED:-false}` and `STRIPE_DRIVER: ${STRIPE_DRIVER:-fake}` (compose:61-62). billing.service.ts reports them separately (`driver: this.stripe.isReal ? 'real' : 'fake'`, billing.service.ts:155; `billingEnabled: await this.settings.billingEnabled()`, :156) but never asserts real-driver when enforcement is on.
- **impact**: If an operator flips Subscriptions ON in the admin UI but has not switched STRIPE_DRIVER to real (the default is fake), enforcement gates engage while checkout/customer-portal calls hit the FakeStripeDriver, which returns canned IDs and records no real charge. No security/data breach (webhooks are still HMAC-verified when real), but tenants could be gated/upgraded against a billing backend that never actually charges — a monetization-correctness foot-gun. Low because billing is OFF by default at launch per the roadmap.
- **fix**: When PlatformSettingsService.setBillingEnabled(true) is called, refuse (or loudly warn in the admin UI) unless the resolved Stripe driver isReal; surface a mismatch banner on the Subscriptions admin page.

## [INFO] MFA_MASTER_KEY format (64-hex) is validated at MfaService construction, not at env load
- **file**: `apps/api/src/config/env.ts:278-286 vs apps/api/src/support/mfa.service.ts:31-33`
- **verified**: static | **confidence**: high
- **evidence**: env.ts only enforces presence in prod (`required('MFA_MASTER_KEY')`) and does not run the 64-hex .validate() that secrets.ts defines for the same key (secrets.ts:170-171). The hex/length check lives in MfaService: `if (!/^[0-9a-fA-F]{64}$/.test(hex)) throw new Error('MFA_MASTER_KEY must be 64 hex chars (32 bytes).');` (mfa.service.ts:31-33).
- **impact**: A malformed MFA_MASTER_KEY (wrong length / non-hex) passes loadEnv() and only fails when the support/MFA module instantiates. That is still boot-time (DI builds the module at startup) and fail-closed, so impact is limited to a slightly later, less obvious failure point than the other secrets. Noted for consistency, not a vulnerability.
- **fix**: Optional: add the same `/^[0-9a-fA-F]{64}$/` validation in env.ts when reading MFA_MASTER_KEY so all secret validation is centralized and fails at the earliest point.
