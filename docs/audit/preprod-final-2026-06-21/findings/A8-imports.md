# A8-imports

The import pipeline is, on the whole, defensively built: MARC binary slicing clamps offsets and tolerates missing terminators, fast-xml-parser 5.8.0 is used with safe defaults (no DTD/external-entity processing, so no XXE on MARCXML), custom-field keys are locked to /^[a-z][a-z0-9_]{1,49}$/ (no __proto__ prototype pollution), int4/money ranges are pre-checked, references are tenant-scoped via the per-job tenant client, and a crash-recovery sweep prevents wedged batches. BUT the headline zip-bomb defense the prompt asked me to re-verify is NOT actually effective, and the column cap that backstops it is missing on the CSV/TSV/MARC path. Two real OOM/DoS vectors remain, plus a low-severity transform crash/data-corruption bug. The recurring theme matches the audit's warning: the comments confidently claim a defense ("reject pathological dimensions BEFORE materializing", "guards against zip-bombs") while the actual code applies the check too late (xlsx) or not at all (CSV columns). All findings are owner/admin-reachable (the import API is role+feature gated), but the worker is shared by all tenants and all five background queues, so a single malicious upload has cross-tenant blast radius.

## [HIGH] xlsx decompression bomb OOMs the shared worker — dimension check runs AFTER exceljs fully inflates every zip entry  _[skeptic: confirmed high]_
- **file**: `apps/api/src/import/parsers/xlsx-parser.ts:36-72`
- **verified**: static | **confidence**: high
- **evidence**: parseXlsx calls `await wb.xlsx.load(ab)` (line 43) and ONLY THEN checks colCount/rowCount against IMPORT_MAX_COLUMNS/ROWS (lines 52-72). The comment at lines 55-60 admits 'exceljs has already parsed the model by here'. exceljs 4.4.0 (node_modules/.pnpm/exceljs@4.4.0/.../lib/xlsx/xlsx.js:279-308) iterates every zip entry and does `content = await entry.async('string')` — fully inflating each entry (sheet1.xml, sharedStrings.xml) into a single JS string with NO decompression-size limit — before the worksheet/sharedStrings SAX parse even builds the row model. The 64MB Multer cap (IMPORT_MAX_UPLOAD_BYTES) bounds only the COMPRESSED file; a deflate stream reaches ~1000:1, so a 64MB xlsx can inflate to tens of GB inside load(). import.constants.ts:13-16 and xlsx-parser.ts:55-60 both claim this is the zip-bomb defense, but the check is unreachable before the OOM.
- **impact**: A single crafted xlsx (owner/admin upload, validate OR commit phase) exhausts the worker heap during exceljs load(). V8 aborts the process on OOM — uncaughtException in worker.ts:275 cannot catch it. worker.ts runs the import, email, scheduled-jobs, maintenance, and export consumers in ONE process (lines 149-199), and the import worker is concurrency 1 (import-worker.ts:263). So one upload simultaneously kills email delivery, reservation-expiry/Stripe-retry cron, exports, and all queued imports for EVERY tenant. Cross-tenant denial of service.
- **fix**: Cap decompression before/while inflating: either pre-scan the zip central directory and reject when the sum of uncompressed entry sizes exceeds a ceiling (and reject any single entry whose uncompressed/compressed ratio is implausible), or switch to exceljs's streaming WorkbookReader (xlsx.read with a worksheets:'emit' stream) and abort once cumulative rows/bytes pass IMPORT_MAX_ROWS — so the cap is enforced DURING inflate, not after the model is fully in memory. Also run the parse in a child process / with a worker --max-old-space-size so an OOM can't take the whole shared worker down.
- **skeptic verdict**: real=True sev=high — Independently confirmed; could not refute. exceljs 4.4.0 load() inflates every zip entry fully before any size guard. In node_modules/.pnpm/exceljs@4.4.0/.../lib/xlsx/xlsx.js:280-308, load() iterates `Object.values(zip.files)` and for each non-media entry runs `content = await entry.async('string')` (line 308) — materializing the entire decompressed entry (sheet1.xml, sharedStrings.xml) into one JS string with NO decompression-size or ratio cap (JSZip imposes none). This all happens inside `await wb.xlsx.load(ab)` at apps/api/src/import/parsers/xlsx-parser.ts:43, which runs BEFORE the colCount/rowCount checks at lines 61-72. The code comment at lines 57-60 itself concedes "exceljs has already parsed the model by here," so IMPORT_MAX_COLUMNS/ROWS are unreachable as a zip-bomb defense. The only upstream guard is Multer's 64MB cap (import.controller.ts:70, IMPORT_MAX_UPLOAD_BYTES), which bounds the COMPRESSED upload only; deflate ratios of ~1000:1 let a 64MB file inflate to tens of GB. Blast-radius claims verified: worker.ts:149-199 boots email, scheduled-jobs (reservation-expiry + Stripe-retry cron), import, maintenance, and export consumers in ONE process; import concurrency is 1 (import-worker.ts:263). The worker.ts:275 uncaughtException handler cannot catch a V8 heap-OOM, which aborts the process directly. Net: a crafted xlsx OOMs the shared worker, a cross-tenant DoS. ONE mitigating fact the claim understates: this is NOT unauthenticated — import.controller.ts:47-49 requires an authenticated owner/admin role plus the bulk_import_enabled feature, so the attacker must be a tenant admin. That precondition is exactly why this is high, not critical: serious, cross-tenant, ops-impacting (kills billing retries + reservation expiry for all tenants), but gated behind an authenticated privileged role. No lock, guard, or idempotency prevents it; precondition is reachable; the auditor did not misread.

## [HIGH] IMPORT_MAX_COLUMNS is enforced only for xlsx — CSV/TSV/MARC have no column cap, amplifying a 64MB upload into multi-GB of objects  _[skeptic: confirmed high]_
- **file**: `apps/api/src/import/parsers/tabular.ts:34-81`
- **verified**: static | **confidence**: high
- **evidence**: grep confirms IMPORT_MAX_COLUMNS is referenced ONLY in xlsx-parser.ts (lines 61-64); csv-parser.ts, tabular.ts and marc-parser.ts have zero column-limit checks. buildTableFromMatrix computes `widest` over all rows (lines 53-55), builds a `columns` array of that width (lines 57-60), and for EVERY data row creates a cells Record keyed by all column names (lines 73-77). normalizeHeaders (lines 10-24) also builds a Map over every header cell. csv-parser.ts:tokenize materializes the full matrix with no column or pre-cap-row bound (maxRows is applied only afterward in buildTableFromMatrix:69). The worker re-checks IMPORT_MAX_ROWS as defense-in-depth (import-worker.ts:111) but never re-checks columns. A 64MB CSV that is one giant header of single-char comma-separated columns yields ~33M ParsedColumn objects + a 33M-entry Map + a 33M-key Record per data row — expanding 64MB of input into several GB of live objects, the exact OOM amplification the xlsx column cap was added to prevent.
- **impact**: Owner/admin can OOM the shared worker process with a wide CSV/TSV/MARC file (no compression needed, just the 64MB cap). Same blast radius as the xlsx bomb: all five queues across all tenants die when the process aborts. The documented column-cap defense simply doesn't exist for 4 of the 5 supported formats.
- **fix**: Enforce IMPORT_MAX_COLUMNS in buildTableFromMatrix (and the MARC recordsToTable union-of-keys loop) before allocating the columns/cells structures — throw ParseError once the header/widest width exceeds the cap. Ideally also bound tokenize() to stop accumulating rows once maxRows+1 is reached instead of materializing the entire matrix first.
- **skeptic verdict**: real=True sev=high — CONFIRMED. The IMPORT_MAX_COLUMNS (=512) cap is enforced ONLY in the xlsx parser (apps/api/src/import/parsers/xlsx-parser.ts:61-65), and its own comment states the cap exists specifically to stop a small upload from "expand[ing] to a sheet with millions of rows/columns — building the full string matrix would OOM the worker." That defense is entirely absent for CSV/TSV and MARC: csv-parser.ts -> tabular.ts:buildTableFromMatrix and marc-parser.ts:recordsToTable build their columns array purely from the data (widest-row / union-of-keys) with no column bound. The worker re-checks rows (import-worker.ts:111 `table.rows.length > IMPORT_MAX_ROWS`) but never columns.

Amplification is real and large. Upload is hard-capped at 64MB (IMPORT_MAX_UPLOAD_BYTES, enforced by multer in import.controller.ts:70). A 64MB CSV of single-char comma-separated columns yields ~33M columns. tabular.ts:53-60 builds a 33M-entry ParsedColumn[]; normalizeHeaders (tabular.ts:10-24) builds a 33M-entry Map; csv-parser.ts:tokenize first materializes the entire matrix (the maxRows cap at tabular.ts:69 only limits row COUNT, applied after `widest` and `columns` are computed). Estimated live set 1.5-2GB+ stacked, exceeding the default V8 heap (no --max-old-space-size set; worker run via `tsx src/worker.ts`).

Independently reproduced: running the exact normalizeHeaders + columns-build logic on ~6M single-char columns (~12MB-equivalent, well under the 64MB cap) under --max-old-space-size=512 produced a fatal V8 "heap out of memory" abort. Notably normalizeHeaders disambiguates duplicate labels (a, a_2, a_3...), so even identical column names manufacture N distinct growing strings, worsening the blast.

Blast radius confirmed: worker.ts hosts all five BullMQ consumers (email, scheduled, import, maintenance, export) in ONE process for ALL tenants. A heap OOM is a SIGABRT, not a catchable uncaughtException/unhandledRejection, so it bypasses the graceful-drain handlers (worker.ts:271-278) and kills every queue across every tenant until the orchestrator restarts.

Precondition reachable: any owner/admin of a tenant with bulk_import_enabled (import.controller.ts:48-49). The upload-time preview even byte-slices CSV/TSV to 256KB (import.service.ts:56-59), so the wide file passes preview and detonates later in the worker on the full buffer.

Adjusted to HIGH (not critical): it is an availability/DoS issue requiring an authenticated privileged tenant user, with no data loss, double-charge, or cross-tenant data exposure. The CSV/TSV vector is the clear, trivially-weaponizable path; MARC is a weaker variant (needs many distinct tag$code records). Fix as proposed: enforce IMPORT_MAX_COLUMNS on `widest`/`order` before allocating columns/cells in buildTableFromMatrix and recordsToTable, and ideally bound tokenize to maxRows+1.

## [LOW] User-supplied multiSeparators is interpolated into a character class without escaping '-', causing whole-batch crash or silent data mangling
- **file**: `apps/api/src/import/mapping/transforms.ts:200-206`
- **verified**: runtime-probed | **confidence**: high
- **evidence**: splitMulti builds `new RegExp('[' + separators.replace(/[.*+?^${}()[\]\\]/g,'\\$&') + ']')`. The escape set omits '-'. Verified at runtime: multiSeparators='z-a' throws `Invalid regular expression: /[z-a]/: Range out of order in character class`, and multiSeparators='a-z' silently builds `[a-z]` so splitMulti('Hello World','a-z') returns ['H','W'] — splitting on every letter instead of the literal chars a, -, z. multiSeparators flows in unvalidated except `typeof === 'string'` (import.service.ts:319 cleanOptions). The throw is uncaught in mapRow→applyTransform (row-mapper.ts:136) and propagates to executeImport (runner.ts:55, no per-row try/catch) up to the worker catch (import-worker.ts:198), failing the ENTIRE batch rather than one row.
- **impact**: Self-inflicted (owner/admin sets the mapping option), so low severity. The 'Range out of order' variant fails an otherwise-clean batch with an opaque error; the unescaped-'-' variant silently corrupts imported multi-valued data (authors etc.) by splitting on character ranges with no per-row issue raised.
- **fix**: Add '-' to the escaped character set (`/[-.*+?^${}()[\]\\]/g`), or build the alternation from individually-escaped single characters rather than a character class. Wrap the RegExp construction in try/catch and surface a precise per-field issue instead of letting it abort the run.
