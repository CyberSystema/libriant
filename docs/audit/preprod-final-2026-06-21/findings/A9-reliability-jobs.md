# A9-reliability-jobs

The worker subsystem is in good shape on the items the prior audits hardened: graceful shutdown has a bounded 25s deadline that force-exits (REL-03), the prod compose healthcheck probes /readyz (real queue+Redis liveness, not an always-200), unhandledRejection/uncaughtException both drain instead of silently killing the loop, the SMTP driver has connect/greeting/socket timeouts, the new Resend HTTP driver has a 15s AbortSignal timeout, throws (rather than crashes) on non-2xx/429 so BullMQ applies exponential backoff, and never logs the API key. The rate limiter keys on X-Real-IP which Caddy overwrites from CF-Connecting-IP behind a Cloudflare-only firewall (not spoofable in this topology), and signup buckets fail closed. Per-tenant sweeps correctly pin connection_limit=1 and use status-guarded CAS updates, so no cross-tenant write or non-idempotent-on-retry issue was found there. The real gap the prior audits MISSED is the email outbox's durability promise: a cold-start / pending-row recovery scan is documented in THREE places (email-worker.ts comment, schema @@index comment, and the row-back-to-pending logic) but is never implemented — unlike imports, which do have an onModuleInit recovery sweep. Combined with a transient Redis failure during queue.add (the producer creates the DB row first), or a crash that outlives BullMQ's stalled-job retries, an outbox row can strand in pending/sending forever with no job to drain it. Two lower-severity correctness issues round it out: the idempotency PENDING marker can expire mid-handler, and the email worker re-sends on a crash between provider-send and the delivered DB write.

## [HIGH] Email outbox has no cold-start / pending-row recovery scan despite being documented in 3 places — stranded rows are never re-delivered  _[skeptic: confirmed high]_
- **file**: `apps/api/src/email/email-worker.ts:36-40, apps/api/src/worker.ts:149-155, packages/db-control/prisma/schema.prisma:723-726`
- **verified**: static | **confidence**: high
- **evidence**: email-worker.ts comment: "On step 4b ... the row going back to `pending` is just so a cold-start recovery scan can see it as 'still owed.'" The schema documents the same: "Worker polls `WHERE status='pending' AND scheduledFor <= now()`; ... this index is the cold-start recovery path." But the worker NEVER polls the table — `startEmailWorker()` only creates a BullMQ `new Worker(...)`; there is no onModuleInit/startup scan and no periodic sweep over EmailOutbox (grep for status:'pending'/'sending' recovery in src/email returns only the write sites). Contrast import-queue.service.ts:67 which DOES have `onModuleInit` cold-start recovery + a periodic `sweepStuckBatches`. Two concrete strand paths: (1) EmailService.enqueue (email.service.ts:98-137) creates the DB row FIRST, then `queue.add`; a transient Redis blip on `queue.add` throws after the row is committed pending — caught per-tenant in member-notifications.job.ts:151-154 and logged as failed, leaving a pending row with no job. (2) A worker crash that outlives BullMQ's stalled-job retry budget removes the job (removeOnComplete/Fail) while the row is still pending/sending.
- **impact**: The durable-outbox guarantee the design rests on is broken in exactly the failure modes the outbox exists to survive. Hold-ready / overdue / password-reset / support-session emails can be silently lost (row stuck pending forever, never retried) after a Redis hiccup during enqueue or a worker crash mid-flight. No alarm fires — the row just sits. For password-reset and support-key emails this is a user-facing lockout/security-notice loss.
- **fix**: Implement the documented recovery: on worker boot and on a periodic timer, scan `EmailOutbox WHERE status IN ('pending','sending') AND scheduledFor <= now()` (the @@index([status, scheduledFor]) already exists) and re-add a BullMQ job (jobId = row.id, so it dedups with any live job) for each, plus age-out 'sending' rows stuck past a threshold back to 'pending'. Mirror import-queue.service.ts's onModuleInit + setInterval(unref) pattern.
- **skeptic verdict**: real=True sev=high — Independently confirmed. The email outbox is designed as a durable outbox whose recovery path is documented in 3 places (email-worker.ts:38 "a cold-start recovery scan can see it as still owed", email-worker.ts:30, and schema.prisma:723-726 "this index is the cold-start recovery path"), but no such scan exists. startEmailWorker() (email-worker.ts:49-100) only constructs `new Worker(...)` with concurrency:5 — there is no onModuleInit startup scan and no periodic setInterval sweep over EmailOutbox. worker.ts:149-155 just calls startEmailWorker(). A grep over apps/api/src/email/ for pending/sending/recovery/sweep returns ONLY the write sites (email-worker.ts:117,149), and the only other emailOutbox reader (support-session-expiry.job.ts:71) does a findMany for dedup, not re-enqueue. The scheduled-jobs registry (jobs/registry.ts) has 9 jobs, none an email-recovery sweep. By contrast import-queue.service.ts:67-74 DOES implement exactly the missing pattern (onModuleInit cold-start recovery + setInterval sweepStuckBatches).

Both strand paths are real and reachable: (1) EmailService.enqueue (email.service.ts:97-137) commits the DB row as `pending` FIRST, then calls queue.add; a transient Redis failure on queue.add throws after the row is committed — and member-notifications.job.ts:151-154 catches per-tenant errors and only logs them, leaving a pending row with no BullMQ job and nothing to find it. (2) defaultJobOptions removeOnComplete:1000 / removeOnFail:5000 (email.service.ts:81-82) plus a `sending` status that is never aged out means a worker crash past BullMQ's stalled budget strands the row.

This silently loses hold-ready/overdue/password-reset/support-session emails after a Redis hiccup during enqueue or a worker crash mid-flight — the exact failure modes the outbox exists to survive — with no alarm. I keep it at high rather than critical: prior-audit REL-04 makes /readyz 503 on a fully-dead worker (ops-detectable), the loss is recoverable manually from the durable rows, and triggering requires a Redis/crash precondition; but the user-facing password-reset/security-notice loss and the broken durability guarantee make high appropriate. The fix (onModuleInit + periodic scan of status IN ('pending','sending') AND scheduledFor<=now(), re-add jobId=row.id, age-out stuck 'sending') is correctly specified.

## [MEDIUM] Idempotency PENDING marker (60s TTL) can expire while the handler is still running, letting a concurrent duplicate re-run a non-idempotent circulation op (double fine/return)
- **file**: `apps/api/src/platform/idempotency.interceptor.ts:19,69,80-94`
- **verified**: static | **confidence**: medium
- **evidence**: `PENDING_TTL_SEC = 60`. On a won claim the handler runs and only on the success `tap` is the key overwritten with the 24h result (lines 80-86). If the handler takes longer than 60s — a slow tenant DB, a contended advisory lock in the loans return/promotion transaction, or a slow checkout — the `__pending__` key EXPIRES mid-flight. A duplicate request (the offline circulation queue replaying, or an impatient double-submit) then SETNX-succeeds because the key is gone (line 69 returns 'OK'), wins its OWN claim, and re-runs the handler. The interceptor's stated purpose (header doc lines 31-32) is to stop "a returned-twice double fine".
- **impact**: Under DB slowness or lock contention, the exact double-action the interceptor was built to prevent (return-twice double fine, double checkout) can still occur on the offline-replay / double-submit path. Low frequency (needs a >60s handler) but it defeats a data-integrity guard on money-affecting routes.
- **fix**: Either (a) raise/refresh the pending TTL while the handler runs (periodic PEXPIRE / longer PENDING_TTL_SEC sized to the route's worst-case latency), or (b) make the protection robust to a lost lock by ensuring the underlying loan/fine writes are themselves keyed for idempotency. At minimum set PENDING_TTL_SEC comfortably above the slowest expected circulation transaction.

## [LOW] Email worker re-sends on a crash between provider send and the 'delivered' DB write (at-least-once with no provider-side dedup)
- **file**: `apps/api/src/email/email-worker.ts:111-136`
- **verified**: static | **confidence**: high
- **evidence**: processOne only short-circuits when `row.status === 'delivered' || 'dead'` (line 111). The flow flips the row to 'sending' (line 115), calls driver.send (line 121), THEN writes 'delivered' (line 128). If the worker crashes (or is force-exited by the 25s shutdown deadline) after driver.send succeeds but before line 128, BullMQ's stalled-job recovery re-delivers the job; the row is still 'sending', so processOne proceeds and re-sends. No Idempotency-Key / dedup is sent to Resend or SMTP.
- **impact**: A patron/library can receive a duplicate of any outbox email (overdue nag, hold-ready, password reset) after a worker crash or a forced shutdown that interrupts an in-flight send. At-least-once email is generally tolerable, so impact is limited to occasional duplicate mail.
- **fix**: Send a stable idempotency token to the provider (Resend supports an Idempotency-Key header; SMTP can reuse a stable Message-ID derived from the outbox id) so the provider dedups a re-sent row, or accept and document the at-least-once semantics.

## [LOW] Scheduled-jobs runner shares one Redis connection between the BullMQ Queue (producer) and the blocking Worker
- **file**: `apps/api/src/jobs/scheduled-jobs.runner.ts:38-42,76-112`
- **verified**: static | **confidence**: medium
- **evidence**: A single `const connection = new Redis(...)` is passed to both `new Queue(QUEUE_NAME, { connection, ... })` (line 42) and `new Worker(QUEUE_NAME, ..., { connection, ... })` (line 111). BullMQ Workers issue blocking commands on their connection; sharing that socket with a Queue producer is a documented BullMQ anti-pattern. The other workers (email/import/export/maintenance) correctly give the Worker its own socket and keep the producer Queue elsewhere.
- **impact**: Mostly benign here because the scheduled Queue is only used at boot (reconcile + register repeatables) and is otherwise idle, so production impact is minimal. Could cause command stalls if the Queue were used at runtime; flagged for correctness/consistency.
- **fix**: Give the scheduled Worker its own ioredis connection separate from the Queue's (duplicate the connection or pass a connection factory), matching the pattern in email-worker.ts / EmailService.
