# A11-desktop-electron

The Electron shell is, on the whole, genuinely well-hardened and the prior audits' "ready" verdict for the core sandbox posture holds up: contextIsolation:true, nodeIntegration:false, sandbox:true, webviewTag:false, webSecurity left at its secure default, no certificate-validation bypass anywhere, a minimal audited contextBridge (no arbitrary IPC/fs/shell/child_process), in-app window creation denied + routed to the system browser, navigation pinned to appOrigin, <webview> attach blocked, every mutating IPC gated by a top-frame + origin check, silent printing constrained to same-origin /print/ routes in a preload-less hidden window, auto-update sha512-verified against a latest.yml fetched over HTTPS, and — importantly — the subscription download gate is enforced SERVER-SIDE (TenantGuard auth + tenant match + BillingService.getDesktopAccess + ForbiddenException), not just in the UI, and is unit-tested. RCE / auth-bypass / cross-tenant via the desktop app were NOT found. What the prior audits missed are lower-tier-but-real supply-chain/transport hardening gaps: (1) the release workflow ships Windows builds with verifyUpdateCodeSignature=false, so a release-channel/GitHub-write compromise auto-installs an arbitrary unsigned exe with no Authenticode gate; (2) the loaded server URL may be plain http:// (env, saved config, or the in-app setServerUrl), sending the session cookie and all traffic in cleartext with no HTTPS enforcement; (3) no will-redirect handler, so a server/HTTP-level 3xx can navigate the privileged main window off-origin (bounded by the sandbox, but a hardening gap); (4) the IPC trust origin (appOrigin) is mutable via setServerUrl; (5) over-broad mac entitlements including an audio-input entitlement the code comments say is unused. None rise to critical on a running product; the Windows update-signature gap is the most serious (high, precondition: signing secrets absent or release channel compromised).

## [HIGH] Windows auto-update ships with code-signature verification disabled (verifyUpdateCodeSignature=false) on unsigned builds  _[skeptic: confirmed high]_
- **file**: `.github/workflows/desktop-release.yml (Windows leg) + apps/desktop/electron-builder.yml:72-81`
- **verified**: static | **confidence**: high
- **evidence**: Release workflow, Windows branch: `echo "::warning::No AZURE_CLIENT_ID — publishing an UNSIGNED Windows build (SmartScreen warns; update signature check disabled)."` then `pnpm exec electron-builder --publish always $VER_FLAG --config.win.verifyUpdateCodeSignature=false`. electron-builder bakes this into app-update.yml, so the SHIPPED client skips electron-updater's Authenticode check (NsisUpdater.verifySignature → _verifyUpdateCodeSignature). The shell auto-downloads + auto-installs on quit unconditionally for packaged builds: main.ts:382-383 `autoUpdater.autoDownload = true; autoUpdater.autoInstallOnAppQuit = true;` and main.ts:399-401 checks on launch + every 6h. sha512 from latest.yml is still verified (mitigates a pure network MITM since latest.yml is HTTPS-from-GitHub), but the publisher-identity gate is gone.
- **impact**: If the GitHub Releases channel is compromised (leaked GITHUB_TOKEN, a malicious release author, or anyone with write to CyberSystema/libriant Releases), an attacker can publish a release with a matching latest.yml + sha512 and every Windows client silently downloads and installs an arbitrary, unsigned executable on next quit — fleet-wide remote code execution on librarian desktops. The Authenticode layer that would normally stop a swapped binary is explicitly off. Ships this way today because the Azure signing secrets are not yet configured.
- **fix**: Sign Windows builds (Azure Trusted Signing secrets) before any production rollout so verifyUpdateCodeSignature stays at its secure default. If shipping unsigned is unavoidable interim, DISABLE auto-update on the unsigned Windows path (don't call autoUpdater for unsigned builds) rather than disabling the signature check — an unsigned auto-updater is the worst of both worlds. Also restrict who can publish GitHub Releases and protect the release tag.
- **skeptic verdict**: real=True sev=high — Independently confirmed; the claim is accurate and not overstated. CODE FACTS (all verified): (1) .github/workflows/desktop-release.yml Windows leg, unsigned branch runs `pnpm exec electron-builder --publish always $VER_FLAG --config.win.verifyUpdateCodeSignature=false` with the warning "update signature check disabled" — this is the DEFAULT shipping path today because the AZURE_* secrets are not configured (SIGNING.md "ship now, sign later"; apps/desktop/electron-builder.yml:72-81 win section documents the same). electron-builder writes verifyUpdateCodeSignature into the packaged app-update.yml, so the shipped NsisUpdater skips electron-updater's Authenticode/publisher-identity check. (2) The client auto-updates unconditionally for packaged builds: apps/desktop/src/main.ts:382-383 `autoUpdater.autoDownload = true; autoUpdater.autoInstallOnAppQuit = true;`, checks on launch and every 6h (main.ts:399-401), and initAutoUpdate() IS actually invoked (main.ts:484; quitAndInstall at main.ts:433). IMPACT: if the GitHub Releases channel is compromised (leaked GITHUB_TOKEN, malicious release author, or anyone with write to Releases), an attacker publishes a release whose latest.yml lists the sha512 of their own malicious unsigned binary; every Windows client then silently downloads and installs it on next quit — fleet-wide RCE on librarian desktops. The Authenticode layer that would normally reject a binary not signed by the legitimate publisher is explicitly off. ADVERSARIAL CHECKS: No existing guard prevents this — unlike macOS, where unsigned => auto-update is fully DISABLED (a safe posture), the Windows path leaves auto-update ENABLED with verification DISABLED (the "worst of both worlds" the fix calls out). The sha512-from-latest.yml check the report itself credits as a mitigation only stops a pure network MITM (latest.yml is HTTPS from GitHub); it does NOT help in the Releases-compromise scenario because the attacker controls latest.yml. Severity HIGH not CRITICAL is correct per the rubric: exploitation requires a precondition (Releases-channel/supply-chain compromise) and there is no unauthenticated network path to RCE against the default-secure feed, so it is an ops/DR + supply-chain risk rather than a directly exploitable bug on the running product. Cited files/lines are accurate; nothing misread or overstated.

## [HIGH] Server URL may be plain HTTP — session cookie and all traffic sent in cleartext, no HTTPS enforcement  _[SKEPTIC: REFUTED — info]_
- **file**: `apps/desktop/src/config.ts:21-29, 58-66; apps/desktop/src/main.ts:76-83,293-299`
- **verified**: static | **confidence**: high
- **evidence**: isValidHttpUrl accepts http: as well as https: — config.ts:25 `return u.protocol === 'http:' || u.protocol === 'https:';`. This validator gates every URL source: LIBRIANT_APP_URL env, the persisted serverUrl, and the renderer/fallback-driven setServerUrl (main.ts:293 `if (!isValidHttpUrl(url)) return ...; config.serverUrl = url; ... loadAppUrl(url);`). openExternal likewise allows http: (main.ts:97). Nothing upgrades or requires https for the loaded app origin; the default is https (config.ts:11) but any override can be cleartext. The shell carries the librarian's authenticated session cookie (silentPrint relies on it riding along: main.ts:115-119).
- **impact**: An operator pointing the shell at an http:// instance (on-prem, LAN, a typo, or a setServerUrl call) transmits the session cookie and all library data over cleartext. A network attacker on the LAN can steal the session, read/modify circulation data, and inject a page into the (sandboxed, but cookie-bearing) renderer. No warning is surfaced. This is a transport-downgrade exposure that a browser would at least flag; the shell silently accepts it.
- **fix**: For production targets, require https for the loaded app origin (allow http only for localhost/dev or behind an explicit opt-in flag). At minimum, refuse http URLs in setServerUrl when app.isPackaged, and surface a clear insecure-connection warning in the fallback/connection UI.
- **skeptic verdict**: real=False sev=info — Code reading confirms the literal facts (config.ts:25 isValidHttpUrl accepts http: and https:; main.ts:293-299 setServerUrl has no app.isPackaged/localhost guard; main.ts:97 openExternal allows http:), but the "high" framing is overstated and not attacker-exploitable on the running product.

Why it is not a real high finding:
1. Not attacker-reachable. setServerUrl is gated by isTrustedSender (main.ts:87-92, 415-417): only the app-origin top frame or the bundled file:// fallback can invoke it. The renderer is sandboxed (sandbox:true, contextIsolation:true, nodeIntegration:false), navigation is pinned to appOrigin (will-navigate, will-attach-webview prevented), and preload.ts exposes only a tiny audited surface. A network/LAN MITM has no primitive to flip a victim from https to http. So there is no "downgrade" an attacker can drive — only operator configuration.
2. The precondition is a deliberate operator/IT choice, not an exploit. Pointing the shell at a chosen server (env LIBRIANT_APP_URL, config JSON, or the fallback connection UI) is the intended self-hosting/on-prem override. http://localhost:3000 is the documented dev default (config.ts:12); the packaged default is https://libriant.com (config.ts:11). Running an on-prem LAN instance over http is a supported operator decision, equivalent to a browser visiting an http site.
3. The actual cleartext-cookie control is server-side, not in the desktop shell. Cookies are set with secure: env.sessionCookieSecure (apps/api/src/auth/cookie.service.ts:13-42 and the admin/impersonation cookie services). For the hosted product the Secure flag is on, so the session cookie will not traverse http at all regardless of what URL the shell loads. Cleartext session exposure requires an operator to BOTH serve over http AND set sessionCookieSecure=false — a self-inflicted self-hosted misconfiguration, not a product vulnerability.
4. The "a browser would flag it" argument is inaccurate: browsers load http origins and transmit non-Secure cookies over them without blocking.

This is a legitimate defense-in-depth hardening idea (refuse/ warn on http for app.isPackaged builds, allow http only for localhost or an explicit opt-in), but it is a low/info hardening nit, not a serious issue with a reachable precondition or DR/ops impact. Marking real=false at the claimed severity; adjusted to info.

## [MEDIUM] No will-redirect handler — a server/HTTP-level 3xx can navigate the privileged main window off-origin
- **file**: `apps/desktop/src/main.ts:246-251`
- **verified**: static | **confidence**: high
- **evidence**: Only `wc.on('will-navigate', ...)` is registered; there is no `will-redirect` handler (grep of main.ts shows will-navigate only). will-navigate does not fire for HTTP-layer (3xx) redirects in Electron — will-redirect does. So a 302 from the loaded origin (or a MITM on an http:// instance) to https://attacker.example can move the main, node-adjacent BrowserWindow to an attacker origin without the external-browser redirect kicking in.
- **impact**: The attacker origin loads in the main window. Bounded by the strong sandbox (contextIsolation/sandbox/nodeIntegration-off hold, so no RCE) and by the IPC origin check (it won't equal appOrigin, so privileged IPC is denied), so this is a hardening gap rather than a breach — but it defeats the intended 'navigation stays on the app origin' guarantee and can be combined with the http downgrade above for phishing inside a trusted-looking app chrome.
- **fix**: Add `wc.on('will-redirect', (event, url) => { if (appOrigin && originOf(url) !== appOrigin && !url.startsWith('file://')) { event.preventDefault(); void openExternal(url); } })` mirroring the will-navigate guard, so off-origin redirects are also pushed to the external browser.

## [MEDIUM] IPC trust origin (appOrigin) is mutable from the renderer, letting a compromised app pivot the full bridge to an attacker origin
- **file**: `apps/desktop/src/main.ts:87-92,188-191,293-299`
- **verified**: static | **confidence**: medium
- **evidence**: isTrustedSender compares the sender frame origin to the mutable global `appOrigin` (main.ts:91 `return originOf(frame.url) === appOrigin;`). setServerUrl (callable from the trusted top frame and from the file:// fallback) reassigns appOrigin via loadAppUrl (main.ts:189 `appOrigin = originOf(url);`) to ANY http/https origin. After that call, the new origin's top frame passes isTrustedSender and gains the entire bridge: openExternal, silent local printing, installUpdate, and further setServerUrl.
- **impact**: If the trusted web app is ever XSS'd (or an http instance is injected), the attacker can call setServerUrl('https://attacker') to make their own server permanently 'trusted' by the shell, gaining persistent access to the privileged bridge (local printer enumeration + silent printing, external-URL opening) across restarts since serverUrl is persisted. Self-perpetuating persistence/pivot; requires an initial foothold so it's an escalation aid rather than a standalone breach.
- **fix**: Gate setServerUrl so it is reachable ONLY from the file:// fallback page (the legitimate reconfiguration surface), not from the live app top frame; e.g. in the handler require frame.url.startsWith('file://') for the mutating set, and treat the live app origin as read-only. Consider an allowlist/confirmation for new origins.

## [LOW] Over-broad macOS hardened-runtime entitlements (audio-input granted though unused; library validation + unsigned-exec memory disabled)
- **file**: `apps/desktop/build/entitlements.mac.plist:8-18`
- **verified**: static | **confidence**: medium
- **evidence**: Entitlements include `com.apple.security.cs.disable-library-validation`, `com.apple.security.cs.allow-unsigned-executable-memory`, and `com.apple.security.device.audio-input` (true). The audio entitlement contradicts the code's own intent — extendInfo in electron-builder.yml:63 states 'Libriant only needs the camera; microphone access is not used.' and the permission allowlist (main.ts:283) does not include microphone-specific media beyond what camera needs. disable-library-validation lets unsigned/third-party dylibs load into the signed app.
- **impact**: Weakens the hardened-runtime guarantees more than necessary: an attacker who achieves local code-injection has an easier time loading unsigned libraries, and the unused mic entitlement grants the app microphone access (privacy surface) for no functional reason. JIT/allow-jit and allow-unsigned-executable-memory are genuinely required by V8; library-validation and audio-input are the questionable ones.
- **fix**: Remove com.apple.security.device.audio-input (the scanner uses the camera only). Re-evaluate com.apple.security.cs.disable-library-validation — Electron typically does not require it; drop it unless a notarization failure proves otherwise. Keep allow-jit/allow-unsigned-executable-memory (V8 needs them).

## [INFO] Silent printing requires no user consent once the renderer is trusted
- **file**: `apps/desktop/src/main.ts:121-180,456-466; apps/desktop/src/preload.ts:44-45`
- **verified**: static | **confidence**: high
- **evidence**: The print bridge drives wc.print({ silent: true, printBackground: true }) (main.ts:170) on a same-origin /print/ route with no per-action user confirmation. It is well-constrained (top-frame + origin gated, same-origin + /print/ path only, no caller fragment, preload-less hidden window, 20s teardown timeout) so it cannot print arbitrary pages or write arbitrary files.
- **impact**: A compromised trusted renderer could spam the default printer with same-origin /print/ routes (paper/toner waste / nuisance), but cannot read files, print arbitrary content, or escape the sandbox. Acceptable for a kiosk circulation desk; noting as residual surface, not a defect.
- **fix**: No change required. If desired, rate-limit silentPrint calls per minute to blunt nuisance abuse.
