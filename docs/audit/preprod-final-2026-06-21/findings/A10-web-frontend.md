# A10-web-frontend

Audited the Next.js web app with focus on the new PWA service worker, offline reads/queue, admin-host routing, branding, and the XSS/CSRF/redirect/secrets surface the two prior "ready" audits would have skipped. The frontend is in solid shape: every user-facing HTML sink I traced is either React-escaped (announcements bodyMarkdown, branding accent colour via React style object, print receipts, system-mode banners) or server-controlled (help articles render checked-in markdown from a non-tenant /help endpoint; the layout <style> comes from assets/theme/tokens.json). SVG upload is blocked at the API (image/svg+xml is absent from every ALLOWED_TYPES list), closing the stored-SVG-XSS path; the assets route has correct path-traversal protection; /api/metrics no longer leaks node_env; healthz/readyz/locales are clean; the only NEXT_PUBLIC_* is the API URL (not a secret); login and verify-email derive their redirect target from server data, not a URL param (no open redirect); a CSP is set in next.config; and admin host-isolation is enforced server-side. The real gaps are all in the new offline/PWA layer. (1) The service worker classifies tenant member-photo/logo URLs (/lbr-api/t/<slug>/storage/...<.jpg|.png>) as "immutable assets" and caches them cache-first into STATIC_CACHE, which the logout cache-wipe (LBR_CLEAR_OFFLINE / clearOfflineCaches) deliberately does NOT clear — so member-photo PII persists on a shared device past logout and is even served stale while online. (2) The runtime page/data caches that DO get wiped are only wiped on explicit logout, not on browser-close or session-cookie expiry, so the default-on "remember me" plus a user who just closes the tab leaves authenticated tenant HTML/JSON cached for the next same-tenant user offline — contradicting the SW's own "wiped on logout" guarantee. (3) The tenant session is protected by SameSite=Lax with no CSRF token; I confirmed no CORS and no state-changing GET endpoints, so it is not exploitable today, but it's a thin, defense-in-depth-free posture. No cross-tenant leak exists in any cache (every cache key includes the tenant slug in the path).

## [MEDIUM] Service worker caches member-photo/logo PII into STATIC_CACHE, which is never wiped on logout
- **file**: `apps/web/public/sw.js:46-50,144-158,26,82`
- **verified**: static | **confidence**: high
- **evidence**: STATIC_RE = /\.(?:css|js|mjs|woff2?|ttf|otf|svg|png|jpg|jpeg|gif|webp|avif|ico)$/i; isImmutableAsset() returns true for any URL whose pathname ends in an image extension. In the fetch handler the immutable-asset branch runs BEFORE the /lbr-api/ branch: `if (isImmutableAsset(url)) { event.respondWith(cacheFirst(request, STATIC_CACHE)); return; }` (line 149) precedes `if (url.pathname.startsWith('/lbr-api/')) {...}` (line 154). Member photos and tenant logos are served at `/lbr-api/t/<slug>/storage/members/<cuid>.jpg` and `/branding/<cuid>.png` (storage refs are `<resourceType>/<cuid><ext>` — apps/api/src/storage/drivers/local-driver.ts:55-57; URLs built in members/[id]/PhotoUploader.tsx:41 and layout.tsx:182). So these PII images are cached cache-first into STATIC_CACHE. But the logout wipe only clears RUNTIME_CACHES: `const RUNTIME_CACHES = [PAGES_CACHE, DATA_CACHE];` (line 26) and LBR_CLEAR_OFFLINE does `Promise.all(RUNTIME_CACHES.map((c) => caches.delete(c)))` (line 82); clearOfflineCaches() in lib/offline.ts:41-44 only deletes keys matching `lbr-pages-`/`lbr-data-`. STATIC_CACHE (`lbr-static-v1`) is excluded from both. The SW header comment claims 'The runtime caches (pages + data) hold tenant data, so they're wiped on logout' — but member-photo PII lands in the non-wiped static cache instead.
- **impact**: On a shared circulation-desk device, a member's photo and the tenant logo remain in the browser cache indefinitely after the librarian logs out, retrievable by the next operator (e.g. via DevTools/cache inspection or simply re-opening the member page offline). Because the entry is cache-first, a stale photo is also served even when back online until the SW version bumps. Same-tenant only (the cache key includes the slug), and it is image data rather than full records, but it is personal data persisting past the logout boundary the SW promises to enforce.
- **fix**: Exclude tenant-scoped storage URLs from the immutable-asset path. Either move the `/lbr-api/` check above `isImmutableAsset` (so anything under /lbr-api/ is treated as tenant data and never goes to STATIC_CACHE), or guard isImmutableAsset with `&& !url.pathname.startsWith('/lbr-api/')`, and route /lbr-api/ storage GETs through the DATA_CACHE (which IS wiped on logout) via staleWhileRevalidate. Restrict cacheFirst/STATIC_CACHE to truly tenant-agnostic paths (/_next/static, /_assets, top-level public assets).

## [MEDIUM] Offline page/data caches only cleared on explicit logout, not on browser-close or session expiry (shared-device stale PII)
- **file**: `apps/web/public/sw.js:114-128,99-112`
- **verified**: static | **confidence**: high
- **evidence**: networkFirstPage caches authenticated tenant HTML into PAGES_CACHE (`cache.put(request, response.clone())`, line 119) and staleWhileRevalidate caches /lbr-api JSON into DATA_CACHE (line 105). These runtime caches are only ever cleared via LBR_CLEAR_OFFLINE / clearOfflineCaches, which is invoked solely from the logout button (apps/web/app/[locale]/t/[slug]/LogoutButton.tsx:32). The session cookie defaults to persistent='remember me on' (apps/web/app/[locale]/login/LoginForm.tsx:31, CookieService.setSession persistent default true — apps/api/src/auth/cookie.service.ts:28), and the documented shared-machine workflow is to UNCHECK remember so the cookie drops on browser close. But dropping the cookie does not run clearOfflineCaches, so the cached tenant pages/JSON survive. When the next user opens the same tenant URL while offline, networkFirstPage serves the previous user's cached member/loan PII from PAGES_CACHE.
- **impact**: A librarian who closes the browser (the recommended shared-desk flow) instead of clicking Sign out leaves authenticated tenant pages and API responses (member lists, loan records, etc.) cached. The next person on that device, offline, is served that PII. Same-tenant (cache keyed by slug, so no cross-tenant leak) and only while offline (online requests are network-first and re-authenticated), which bounds it, but it contradicts the SW's stated 'wiped on logout' security model for the exact shared-device scenario the code calls out.
- **fix**: Clear runtime caches on session loss, not just on the logout button: call clearOfflineCaches() when /auth/me returns 401 (session expired) and/or on the SW 'activate'/page-load when no session cookie is present. Consider not caching full authenticated navigations at all (the offline value is mostly the API data cache), or scope cached pages/data with a per-session marker so a new/absent session can't read the prior one's entries.

## [LOW] Tenant session relies on SameSite=Lax alone — no CSRF token, no defense in depth
- **file**: `apps/api/src/auth/cookie.service.ts:32,43`
- **verified**: static | **confidence**: high
- **evidence**: The tenant session cookie is set with `sameSite: 'lax'` (lines 32, 43) and there is no CSRF token anywhere in apps/web or apps/api (grep for csrf/xsrf returns nothing). All state-changing browser calls are JSON POST/PATCH/DELETE via the same-origin /lbr-api proxy with credentials:'include' (apps/web/lib/api.ts:88-98). I confirmed there is NO CORS configured on the API (no enableCors in apps/api/src/main.ts) and found no state-changing @Get endpoints, so a cross-site request cannot both send the Lax cookie and reach a mutating handler today. Admin and impersonation cookies correctly use SameSite=Strict (admin-cookie.service.ts:26, impersonation-cookie.service.ts:24), so only the tenant plane is on the weaker Lax setting.
- **impact**: Not exploitable as written: SameSite=Lax suppresses the cookie on cross-site POST, and with no CORS a cross-origin credentialed XHR is blocked, so there is no working CSRF path. The risk is purely defense-in-depth — a future regression that adds a permissive CORS policy, a top-level GET that mutates state, or a same-site subdomain takeover would have no second line of defense for tenant write operations.
- **fix**: Add a standard double-submit or header-based CSRF defense for the tenant plane (e.g. require a non-cookie custom header such as X-Requested-With / X-CSRF on all mutating routes — trivial to enforce since all browser writes already go through lib/api.ts and could add the header centrally), and/or tighten the tenant session to SameSite=Strict like the admin/impersonation cookies if the UX (no cross-site top-level entry needed) allows it.

## [INFO] CSP allows 'unsafe-inline' for script-src, weakening XSS containment
- **file**: `apps/web/next.config.mjs:48-66`
- **verified**: static | **confidence**: medium
- **evidence**: The CSP sets `script-src 'self' 'unsafe-inline'` (and style-src 'unsafe-inline'), acknowledged in the comment as needed because 'the App Router emits [bootstrap/hydration inline scripts] without a nonce'. object-src 'none', base-uri 'self', frame-ancestors 'none', and connect-src 'self' are correctly locked down.
- **impact**: If an HTML-injection sink ever regresses (the code does use dangerouslySetInnerHTML for the token <style>, print CSS, and help-article HTML), 'unsafe-inline' on script-src means an injected inline <script> would execute — the CSP would not contain it. No such sink is currently reachable with user input (verified: all three dangerouslySetInnerHTML sources are server-controlled), so this is hardening, not an active vulnerability.
- **fix**: Move to a nonce-based CSP via request-scoped middleware so 'unsafe-inline' can be dropped from script-src (Next.js App Router supports nonce propagation through middleware). At minimum keep the help-article ingest pipeline (the one HTML sink that renders rendered markdown) sanitized/whitelisted so it can never emit <script> regardless of CSP.
