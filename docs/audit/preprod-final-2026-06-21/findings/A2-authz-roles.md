# A2-authz-roles

Audited every guard (AuthGuard, TenantGuard, RolesGuard, AdminAuthGuard, AdminRolesGuard, PlanGuard, QuotaInterceptor, EmailVerifiedGuard, SupportSessionGuard, NonProductionOnlyGuard) and built a full route→guard matrix across all 43 controllers. The authorization plane is in strong shape and the prior Reflector-DI 500 regression has been correctly avoided: the standalone-referenced guards (RolesGuard/TenantGuard/AdminRolesGuard/EmailVerifiedGuard) construct Reflector directly or use the controlDb singleton (no constructor DI), while the DI-injected PlanGuard/QuotaInterceptor are properly registered+exported by PlansModule and every consumer imports it, so DI resolves. Roles are always re-read from the control DB (never from the JWT) so revocation/downgrade is immediate; cross-tenant IDOR is structurally prevented by db-per-tenant (resource IDs from the path are queried against the tenant's own Prisma client); every mutating /admin/* route carries @AdminRoles('owner') (support-only routes like redeem are intentionally any-admin); impersonation bypass of role/plan/quota gates requires a signed JWT bound to a live, tenant-matched support_sessions row; and the admin session cookie is __Host-scoped so the admin API is unreachable from the public host regardless of Host header. Two non-critical observations remain: the least-privileged "volunteer" role can fully mutate core circulation/catalog data, and the new admin-host isolation is enforced only in the web UI layer (the API has no host check, relying solely on the host-scoped cookie).

## [MEDIUM] "volunteer" role (explicitly "limited rights") can create/edit/archive all core data — catalog, members, loans, reservations, copies, custom records — no @Roles gate
- **file**: `apps/api/src/catalog/books.controller.ts:33-82 (also members.controller.ts:42-134, loans/loans.controller.ts:47-128, reservations/reservations.controller.ts:49-126, catalog/copies.controller.ts:35-75, catalog/authors.controller.ts:27-65, customization/collection-records.controller.ts:33-92)`
- **verified**: static | **confidence**: low
- **evidence**: BooksController is `@Controller('t/:slug/catalog/books') @UseGuards(TenantGuard)` with NO @Roles on `@Post()/@Patch(':id')/@Delete(':id')`, and the handlers pass only `tenant` to the service — role is never read. The UserRole enum (packages/db-control/prisma/schema.prisma:41-46) defines `volunteer // limited rights` as the lowest role, and TenantGuard only proves membership, not role. By contrast staff/settings/branding/import/audit/collections-definitions ARE `@Roles('owner','admin')`-gated, and storage-demo.controller.ts:251 explicitly floors sensitive-file reads above `volunteer` (`if (!user || user.role === 'volunteer') throw ForbiddenException`). So a volunteer who is blocked from viewing a member's photo file can still PATCH/DELETE that member record, edit/delete any book, and check out/return/mark-lost loans.
- **impact**: A library account intended as 'limited rights' (e.g. a temporary helper) can destructively mutate the entire catalog, member roster, and circulation ledger. Not a cross-tenant breach (db-per-tenant isolates it) and requires an admin to have created the volunteer account, but it contradicts the documented role semantics and the privacy floor the same codebase applies to member files.
- **fix**: Decide the intended volunteer capability explicitly. If volunteers should only do circulation, add `@UseGuards(RolesGuard) @Roles('owner','admin','librarian')` to the destructive catalog/members routes (POST/PATCH/DELETE) and keep loans open; if the data routes are genuinely meant for all roles, document that and reconcile it with the TEN-06 volunteer file floor so the model is consistent. At minimum gate DELETE/archive and member status changes above volunteer.

## [LOW] Admin-panel host isolation is enforced only in the Next.js web layer; the admin API has no host/Host-header check and relies solely on the __Host- cookie
- **file**: `apps/web/app/[locale]/admin/layout.tsx:28-34 (API side: apps/api/src/admin/admin-auth.guard.ts:29-64, no host check anywhere in /admin/* controllers)`
- **verified**: static | **confidence**: medium
- **evidence**: Commit cd7c9cb added the only host gate, in the web layout: `const adminHost=(process.env.ADMIN_HOST??'')...; if(reqHost && reqHost!==adminHost) notFound();`. The API admin controllers (`@Controller('admin/...')`) are matched on ANY host; AdminAuthGuard authenticates purely from the signed `__Host-libriant_admin` cookie (admin-auth.guard.ts:31-45) with no Host comparison. The commit message asserts 'the admin API was unreachable cross-host' but that property comes only from the cookie's __Host- prefix (env.ts:272-275, set with path:'/' and no Domain in admin-cookie.service.ts:22-30), not from any API-side host enforcement.
- **impact**: The defense currently holds because a __Host- cookie set on admin.<apex> is never sent to the public apex, so /admin/* on the public host gets 401. But the protection is implicit and single-layered: if ADMIN_COOKIE_NAME is ever overridden to drop the __Host- prefix, or a future change loosens the cookie scope/Domain, the admin API becomes reachable on the public host with no second barrier. The web 404 is cosmetic and does not protect the API.
- **fix**: Add a defense-in-depth host check on the API admin surface (a middleware/guard that 404s /admin/* when the request Host !== ADMIN_HOST, mirroring the web layout and the TenantMiddleware adminHost handling at tenant.middleware.ts:121), and add a startup assertion that the admin cookie name retains the __Host- prefix in production. Do not trust X-Forwarded-Host for this — use the validated Host that Caddy preserves.

## [INFO] GET /t/:slug/plan and /plan/usage (effective-plan + raw override internals) are reachable by any tenant role including volunteer, but are 404'd in production by NonProductionOnlyGuard
- **file**: `apps/api/src/plans/plan-demo.controller.ts:65-105`
- **verified**: static | **confidence**: medium
- **evidence**: PlanDemoController is `@UseGuards(NonProductionOnlyGuard, TenantGuard, PlanGuard)` and the guard returns 404 outside development (`private readonly enabled = loadEnv().nodeEnv !== 'production'; if(this.enabled) return true; throw new NotFoundException()`). The guard is listed FIRST so prod requests 404 before TenantGuard warms a pool. Verified nodeEnv defaults to non-production only when NODE_ENV is unset; in prod NODE_ENV=production so these routes are absent.
- **impact**: None in production (routes 404). Noted only because the plan/usage read has no @Roles even in dev and exposes plan-source internals; confirm NODE_ENV=production is actually set for the API service at deploy time (the project has a documented web-side NODE_ENV gotcha) so this guard's enabled flag computes false.
- **fix**: No action required if NODE_ENV=production is guaranteed for the API container. Optionally fail-closed: have NonProductionOnlyGuard treat an unrecognized/empty NODE_ENV as production rather than dev, so a missing env var hides the demo routes instead of exposing them.
